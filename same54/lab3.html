Lab 3: Add a Shell and Temperature Sensor to Your Project

Purpose​

In this lab, you will enable the Zephyr shell over UART, inspect the running system with built-in shell commands, and add and configure a driver for the AT30TSE758 temperature sensor on the Microchip IO1 Xplained Pro.

Overview​

Lab 3 builds on the two-thread project from Lab 2. First you will enable the Zephyr shell and use it to inspect devices and threads at runtime. Next you will enable the I²C shell, find the temperature sensor on the bus, and describe it in a Devicetree overlay. Finally you will enable Zephyr's sensor subsystem and read converted temperature values from the shell.

Procedure​

Step 3.1: Enable and Explore the Zephyr Shell​

3.1.1: Open prj.conf and add the following line to enable the Zephyr shell subsystem:​

CONFIG_GPIO=y
CONFIG_SHELL=y

3.1.2: Open src/producer.c and src/consumer.c and remove the printk calls in the thread functions so the shell prompt is not obscured by continuous output:​

In producer.c:

        if(counter++>=10) {
            printk("(producer) Putting %d into message queue\n", data);
            k_msgq_put(notifyMsgQueue, &data, K_NO_WAIT);
            data++;
            counter = 0;
        }

In consumer.c:

    while (1) {
        k_msgq_get(notifyMsgQueue, &data, K_FOREVER);
        printk("(consumer) Received data: %d\n", data);
    }

3.1.3: Build and flash the updated firmware:​

  • Ubuntu
  • macOS
  • Windows
(.venv) $ west build -p always -b sam_e54_xpro application
(.venv) $ west flash 
(.venv) $ west build -p always -b sam_e54_xpro application
(.venv) $ west flash 
(.venv) PS C:\...\zephyrproject> west build -p always -b sam_e54_xpro application
(.venv) PS C:\...\zephyrproject> west flash

3.1.4: Open the Serial Monitor. To use the interactive shell you must configure line endings to CRLF (both send and receive). Set this option in the Serial Monitor settings panel before connecting.​

Once connected you should see the uart:~$ prompt. Type help to list all registered shell modules and their top-level commands:

uart:~$ help

3.1.5: List all registered Zephyr devices by typing the following command at the shell prompt:​

uart:~$ device list

Observe the output - every driver that was compiled into the image and successfully initialised will appear here.

3.1.6: List all active Zephyr threads and their current state, priority, and stack usage:​

uart:~$ kernel thread list

Notice that the producer and consumer threads appear with auto-generated numeric names. The next step will make them easier to identify.

3.1.7: Open main.c and add the following two calls immediately after the k_thread_create calls for the producer and consumer threads:​

	k_tid_t producer_tid = k_thread_create(&producerThread_data,
                         producerThreadstack_area,
                         K_THREAD_STACK_SIZEOF(producerThreadstack_area),
                         producerThread,
                         (void*)&led, (void*)&consumerQueue, (void*)NULL,
                         PRIORITY, 0, K_NO_WAIT);

	k_tid_t consumer_tid = k_thread_create(&consumerThread_data,
                          consumerThreadstack_area,
                          K_THREAD_STACK_SIZEOF(consumerThreadstack_area),
                          consumerThread,
                          (void*)NULL, (void*)&consumerQueue, (void*)NULL,
                          PRIORITY, 0, K_NO_WAIT);

	k_thread_name_set(producer_tid, (const char *)"producer");
	k_thread_name_set(consumer_tid, (const char *)"consumer");

	while (1) {
		k_msleep(SLEEP_TIME_MS);
	}

3.1.8: Rebuild, flash, and rerun kernel thread list in the shell. The producer and consumer threads should now appear with their human-readable names.​

uart:~$ kernel thread list

3.1.9: CHALLENGE - Stack Usage Analysis​

While looking at the kernel thread list output, examine the unused stack column for your producer and consumer threads. The STACKSIZE macro in main.c is currently set to 1024 bytes for both threads.

Consider: is 1024 bytes the right size? If the unused stack is very large you are wasting RAM. If it is very small the thread is at risk of a stack overflow. Try reducing STACKSIZE for one or both threads and observe whether the firmware still builds and runs correctly. What is the minimum safe stack size for each thread?

Step 3.2: Find the Temperature Sensor on the I²C Bus​

The Microchip IO1 Xplained Pro includes an AT30TSE758 temperature sensor. In this lab, Zephyr's generic LM75-compatible driver will expose the sensor through the sensor subsystem.

3.2.1: Connect the IO1 Xplained Pro board to the EXT2 header on the SAME54 Xplained Pro, and then press the RESET button.​

The EXT2 header is connected to a SERCOM peripheral that the SAME54 board definition already configures as an I²C controller.

3.2.2: Open prj.conf and add the following options to enable the I²C subsystem and its shell commands:​

CONFIG_GPIO=y
CONFIG_SHELL=y
CONFIG_I2C=y
CONFIG_I2C_SHELL=y

3.2.3: Build and flash the updated firmware:​

  • Ubuntu
  • macOS
  • Windows
(.venv) $ west build -p always -b sam_e54_xpro application
(.venv) $ west flash 
(.venv) $ west build -p always -b sam_e54_xpro application
(.venv) $ west flash 
(.venv) PS C:\...\zephyrproject> west build -p always -b sam_e54_xpro application
(.venv) PS C:\...\zephyrproject> west flash

3.2.4: Scan the I²C bus from the UART shell:​

uart:~$ i2c scan i2c0

The device at address 0x4f is the IO1 board's temperature sensor.

3.2.5: Read two bytes from the temperature register at address 0x00:​

uart:~$ i2c read i2c0 4f 00 2

Use i2c help to see the other commands provided by the I²C shell:

uart:~$ i2c help

Step 3.3: Add a Devicetree Overlay for the Temperature Sensor​

The bus scan confirms that hardware responds at 0x4f. Next, describe that device to Zephyr so the LM75-compatible driver can bind to it.

3.3.1: Create a boards/ directory inside your application directory and create the overlay file:​

  • Ubuntu
  • macOS
  • Windows
(.venv) $ mkdir -p application/boards
(.venv) $ touch application/boards/sam_e54_xpro.overlay
(.venv) $ mkdir -p application/boards
(.venv) $ touch application/boards/sam_e54_xpro.overlay
(.venv) PS C:\...\zephyrproject> mkdir application\boards
(.venv) PS C:\...\zephyrproject> ni application\boards\sam_e54_xpro.overlay

3.3.2: Open application/boards/sam_e54_xpro.overlay and add the following Devicetree content:​

&sercom7 {
    /* sercom7 is enabled as I2C in the base DTS. */
    #address-cells = <1>;
    #size-cells = <0>;

    temp_sensor: lm75@4f {
        compatible = "lm75";
        reg = <0x4f>;
        status = "okay";
    };
};
info

The AT30TSE758 is register-compatible with the LM75 for the operations used in this lab, so the generic lm75 binding and driver can communicate with it.

3.3.3: Append the three highlighted options to prj.conf to enable the sensor subsystem, its shell commands, and the LM75 driver. Your Lab 3 configuration should now include all of the following:​

CONFIG_SHELL=y
CONFIG_I2C=y
CONFIG_I2C_SHELL=y
CONFIG_SENSOR=y
CONFIG_SENSOR_SHELL=y
CONFIG_LM75=y

3.3.4: Perform a pristine build, flash the board, and reopen the Serial Monitor:​

  • Ubuntu
  • macOS
  • Windows
(.venv) $ west build -p always -b sam_e54_xpro application
(.venv) $ west flash 
(.venv) $ west build -p always -b sam_e54_xpro application
(.venv) $ west flash 
(.venv) PS C:\...\zephyrproject> west build -p always -b sam_e54_xpro application
(.venv) PS C:\...\zephyrproject> west flash

Run device list and confirm that lm75@4f appears as an initialized device:

uart:~$ device list

Step 3.4: Read the Temperature Through the Sensor Subsystem​

3.4.1: Query the sensor by its Devicetree node name:​

uart:~$ sensor get lm75@4f

3.4.2: Query the same sensor by its temp_sensor node label:​

uart:~$ sensor get temp_sensor

Place your finger over the sensor and rerun either command several times. Observe how the reported ambient temperature changes.

3.4.3: CHALLENGE - Read the Sensor from the Producer Thread​

Using what you learned in the previous labs, update producer.c to read the current temperature and deliver it to consumer.c through the message queue.

At the top of producer.c, add the device and sensor APIs between the existing Zephyr includes and producer.h:

#include <zephyr/kernel.h>
#include <zephyr/drivers/gpio.h>
#include <zephyr/device.h>
#include <zephyr/drivers/sensor.h>
#include "producer.h"

Below the includes and before producerThread(), get the Devicetree node and create a device handle:

#include "producer.h"

#define LM75_NODE DT_NODELABEL(temp_sensor)

static const struct device *const temp_dev = DEVICE_DT_GET(LM75_NODE);

void producerThread(void *inLed, void* inMsgQueue, void*) {
    ...

Inside the existing if(counter++>=10) block, fetch a sample and retrieve the converted ambient-temperature value before placing data in the message queue:

        if(counter++>=10) {
            struct sensor_value temp_val;

            sensor_sample_fetch(temp_dev);
            sensor_channel_get(temp_dev, SENSOR_CHAN_AMBIENT_TEMP, &temp_val);
            printk("Temperature: %d.%06d C\n", temp_val.val1, temp_val.val2);
            k_msgq_put(notifyMsgQueue, &data, K_NO_WAIT);
            data++;
            counter = 0;
        }
tip

Before reading the sensor in application code, use device_is_ready(temp_dev) and check the return values from sensor_sample_fetch() and sensor_channel_get().

Results​

You enabled Zephyr's shell and I²C support, found the IO1 Xplained Pro temperature sensor on the bus, described it in a Devicetree overlay, and read converted temperature values through the sensor subsystem.

Summary​

This lab introduced three useful Zephyr development tools:

  • The shell provides runtime inspection and interactive access to enabled subsystems.
  • An I²C bus scan can confirm a peripheral's address before a driver is configured.
  • Devicetree and Kconfig work together to describe hardware and include its driver. Once the LM75-compatible device is initialized, both the sensor shell and application code can use Zephyr's common sensor API instead of accessing raw registers directly.
